# Architecture

```
browser ──► web (nginx: SPA + /api proxy, :8080) ──► api (NestJS, /api/v1) ──► postgres
                                                        │  ▲ SSE (Redis pub/sub)   redis (BullMQ)
                                                        ▼  │
                                                      worker (same image, dist/worker)
                                                        │ internal HTTP + X-Service-Token
                                        ┌───────────────┼────────────────┐
                                      vision          recon            geometry
                                   (photo quality) (COLMAP 4.2.1;    (mesh, inspect, process,
                                                    CUDA if GPU)      game-map, export)
                                        └──────── named volume /data ────┘
```

| Service | Responsibility | Tech |
|---|---|---|
| web | UI; same-origin proxy so cookies and SSE just work | React 19, Vite, R3F/drei, Tailwind 4, TanStack Query, Zustand, RHF+Zod |
| api | Auth, projects, uploads, job creation, SSE, asset downloads, OpenAPI (`/api/docs`) | NestJS 11, Prisma 6, Pino |
| worker | Runs jobs; drives Python services; registers validated assets | NestJS app context, BullMQ |
| vision | Blur, exposure, contrast, ORB detail, near-duplicate detection, capture advice | FastAPI, OpenCV |
| recon | COLMAP pipeline, one job at a time, persisted status, cancellation | FastAPI, COLMAP image |
| geometry | Meshing, inspection, processing ops, game-map derivation, export packages | FastAPI, Open3D, trimesh |
| postgres | Source of truth (users, projects, uploads, jobs, events, assets) | PostgreSQL 16 |
| redis | Queues and job event pub/sub | Redis 7 (AOF) |

The prompt suggested five Python services; geometry, game-map and export share one container because they
share the same heavy Open3D stack (separate modules: `inspect.py`, `process.py`, `gamemap.py`, `export.py`).

## Storage

All binary data lives on the `data` volume, addressed by **storage keys** generated by the API:

```
projects/<projectId>/uploads/<uuid>.jpg | .thumb.webp
projects/<projectId>/jobs/<jobId>/...        (every job writes only under its own prefix)
recon-jobs/<jobId>.json                      (recon service status, survives restarts)
```

Keys never leave the backend (`publicAsset` strips them). Both Node (`StorageService.path`) and Python
(`resolve_key`) reject anything that is not a plain relative key. Inputs are never modified: each processing
step writes a new asset with `parentAssetId` and the recorded operations.

## Jobs

One `Job` table (`kind`: reconstruction | processing | gamemap | export) and a `JobEvent` timeline.
States: `queued → validating → running → processing → (exporting) → completed`, plus `failed`,
`cancelling → cancelled`. Every change goes through `JobsService.transition`, which validates with
`assertTransition` and applies an optimistic `updateMany where status = <read status>` so concurrent cancels
can't be lost. Each change is published on Redis `job:<id>` and streamed by `GET /jobs/:id/events` (SSE);
the UI falls back to polling if the stream fails.

Reconstruction flow (worker `ReconstructionRunner`): validate photos and disk → `POST recon /jobs/:id`
(idempotent) → poll every 2 s, mirroring stage and *measured* progress → geometry `/mesh` → re-inspect
outputs → register assets → `completed`. A job is only completed after its outputs exist and reloaded.

Resilience:
- **Worker restart**: shutdown hooks stop runners at a safe point and re-queue the BullMQ job
  (`moveToDelayed`); the next worker re-attaches to the still-running COLMAP job. Verified with
  `docker compose restart worker` mid-reconstruction.
- **Recon restart**: in-flight jobs are marked `service_restarted` from their status file.
- **Orphans**: on startup, live DB jobs unknown to the queue are failed with `worker_lost`.
- Retries happen only for connection failures to Python services, never for COLMAP failures.
